# v9-body STAGE 1 — shape-parametric multi-scale conv body, perf spike

worktree: `magic-crystal-v9body`, branch `v9-body`, off `main` @ f012514f
(HANDOFF.md → RULING 07-21 + AMENDMENT: interior multi-scale legal, output
res free, render res 640×480, no upscaling).

## What was built

`packages/scrying-glass/src/rdirect_unet.rs` — a new net body beside the
existing per-pixel `rdirect` MLP (`rdirect.rs`/`rdirect_live.rs`, the body
HANDOFF.md's v8d capacity verdict sealed as unable to reach the resid 0.035
bar for want of any spatial receptive field). U-Net style: encoder
downsamples (default 3 scales — full/2/4), 3×3 convs, ReLU, skip
connections, decoder back to output res via bilinear resize + a learned
conv (never a bare resize as the last drawing op). Built on the same house
MPSGraph tensor-path pattern `rdirect_live.rs` uses [source: packages/scrying-glass/src/rdirect_live.rs] (`MPSGraph`, per-frame
placeholder/constant graph, `runWithMTLCommandQueue…` for the honest
bring-up call, plus a compiled-executable GPU-only split mirroring
`rdirect_live.rs`'s own S3 shift).

Inputs = the v7 feature set already built by `rdirect::hist_features_split`
(1-ray evidence taps + gbuffer + reprojected history, `HIST_FEATURES_SPLIT`
= 39 channels) plus 2 new motion-vector channels (`MOTION_VECTOR_CHANNELS`)
— 41 input channels total, read as image channels (not a flat per-pixel
vector) so the conv stack can see a pixel's neighbours, the exact thing the
per-pixel body never had. Weight/activation storage is fp16
(`half::f16`) end to end on the graph.

IRON: every dimension is a field on `UnetConfig` with a documented default
— `n_scales`, `widths` (per-scale channel count), `kernel`, `in_channels`,
`out_channels`, `render_w/h` (default 640×480, the evidence/trace side),
`output_w/h` (default = render res; free per the amendment — a different
value resizes the decoder's last feature map to that grid and runs one more
learned conv before the 1×1 output head, never a bare interpolation as the
last op). No dimension is a literal in the graph-builder function.

## Spike harness

`packages/scrying-glass/examples/rdirect_v9_spike.rs` — offscreen (own
system Metal device, `UnetLive::from_system`, no window — WINDOW BAN),
untrained He-init weights, 640×480 render/output res. For each config: 8
warmup calls, then 40 timed calls of two forward paths:

- **wall** — `forward_cpu_roundtrip` (`runWithMTLCommandQueue_feeds_…`),
  the honest CPU-roundtrip number: host→device feed, per-frame graph
  dispatch, device→host readback. This is the same class of number
  `docs/perf/2026-07-18-neural-live-n0.md` calls "n0d" (the pre-optimization
  bring-up wall).
- **gpu** — `forward_gpu_ms`, a compiled `MPSGraphExecutable` encoded onto [source: packages/scrying-glass/examples/rdirect_v9_spike.rs]
  its own fresh `MTLCommandBuffer`, `commit` + `waitUntilCompleted`, then
  `MTLCommandBuffer.GPUEndTime − GPUStartTime`. This mirrors
  `rdirect_live.rs`'s own S3 shift, which found the live rdirect net's
  wall was ~40ms while its GPU-only forward was ~6ms — the wall was CPU
  encode/wait, not GPU compute. The budget verdict below is judged on the
  **gpu** number for the same reason: the CPU-side per-frame encode is a
  known, already-solved-once class of cost (S1/S2/S9 in
  `docs/perf/2026-07-18-neural-live-n0.md`), not a property of this body's
  shape, and stage 2+ of this lane does not yet wire the zero-copy/pooled
  present-path plumbing that made the existing net's wall cheap.

## Reading the numbers

The GPU-only forward for A/B/C sits at 3.4–4.3ms, well under the 9.07ms
budget, with 2–2.6× headroom even at C-med. D-large (roughly 3× C-med's
parameter count) crosses the budget at 11.36ms GPU-only — the real ceiling
sits between C-med (163k params) and D-large (494k params), not at the
first config tried. This is the opposite finding from the DLSS-4
reference-width spike: `~/projects/dlss4-bringup/REPORT.md` measured ONE
window-attention block at documented DLSS widths at 73–83ms clean, 8–9×
over the WHOLE net's budget, on one of eleven such layers
[source: ~/projects/dlss4-bringup/REPORT.md]. This spike's widths are
M1-sized from the start (12–112 channels per scale vs. DLSS's documented
32–160 with attention blocks), and even the largest tested config's
GPU-only cost (11.36ms) is only ~1.25× over budget, not two orders of
magnitude.

The wall numbers (25–46ms median) are honest and match the shape of the
existing net's own pre-optimization bring-up number (n0d, ~41.8ms total
frame, of which the net stage alone was ~27ms)
[source: docs/perf/2026-07-18-neural-live-n0.md]. They are NOT the number
this stage picks a config against — `docs/perf/2026-07-18-neural-live-n0.md`'s
own S1/S2/S3/S9 shifts already proved that gap is MPSGraph's per-frame CPU [source: docs/perf/2026-07-18-neural-live-n0.md]
encode/wait, solved once by pooled zero-copy buffers + a dedicated queue +
frame-overlap pipelining, none of which this stage 1 body has wired yet
(that plumbing is a live-path concern, not a body-shape concern — stage 2
of this lane is trainer wiring, not live integration). Wiring this body
into the same pooled/pipelined present path the existing net already
proved out is explicitly OUT OF SCOPE for this lane's three stages and is
flagged here as the honest next-integration cost, not hidden.

## Chosen config + rationale

**C-med, widths=[24,40,64], n_scales=3, kernel=3** — the largest of the
four tested configs that stays under the 9.07ms GPU budget (4.29ms median,
5.57ms p95 — see table). Set as `UnetConfig::default()`.

Rationale: A-tiny/B-small leave 5–6ms of budget on the table for no
measured quality gain (untrained spike — quality is not measurable yet);
C-med is the highest-capacity config confirmed under budget by this spike,
and D-large's 11.36ms shows the ceiling is close (not 10× away, unlike the
DLSS-width scenario) — a useful data point for any later width tuning once
stage 2's trainer produces a real quality signal to tune against. C-med is
NOT claimed as globally optimal; it is the largest of the four measured
points that passes, which is what this stage's task asked for ("Pick the
largest config under budget").

## Honest gaps (flagged, not hidden)

- **Live-path integration is not done.** This body runs standalone
  (`UnetLive::from_system`), not through the wgpu-bridged, zero-copy,
  pooled-buffer, frame-overlap path the existing net uses in production
  (`rdirect_live.rs`'s `from_wgpu_queue`/`SharedPool`/`Pipeline`). The wall
  numbers above reflect that absence honestly; they are not a claim about
  what the wired path would cost.
- **Untrained weights.** He-init only — no quality claim of any kind is
  made or implied by this document. Stage 2 (trainer wiring) and stage 3
  (training launch) are separate, later steps of this lane.
- **Output-resolution-free path (`output_w/h != render_w/h`) is built
  (the resize + learned-conv arm in `UnetLive::build`) but NOT exercised by
  this spike** — every measured config used output res = render res =
  640×480. Flagged as untested, not claimed working.
- **fp16 storage is verified to run and produce finite output** (the
  sanity line above) but no numerical-parity check against an fp32
  reference was run this stage — flagged UNVERIFIED for anything beyond
  "it runs and is finite."
