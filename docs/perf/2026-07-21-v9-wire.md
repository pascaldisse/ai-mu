### Tolerance derivation (done BEFORE running — canon law: "re-derive by
hand, never bump-to-match")

The house precedent (`tests/rdirect_live_ordeals.rs`'s N0 GATE 1, the v7
MLP's own CPU-vs-live parity gate) derives its ~1e-3 bound from **f32**
GEMM reassociation, because `rdirect_live.rs` stores weights/activations in
`MPSDataType::Float32`. `rdirect_unet.rs` is different in kind: its own
module doc states "Weight/activation storage is fp16 (`half::f16`) end to
end on the graph" — every constant AND every intermediate the graph
produces is fp16-typed.

IEEE-754 binary16: 1 implicit + 10 explicit mantissa bits (11 bits total
precision) → unit roundoff u16 = 2^-11 ≈ 4.883e-4 (max relative error one
correctly-rounded fp16 value can carry).

UNVERIFIED: Apple's internal accumulation precision for MPSGraph's fp16 conv/resize/
concat ops on this silicon is **not published and not on file in this
repo** — UNVERIFIED whether it accumulates in fp32 internally (the common
tensor-core convention) or fully in fp16 as the module doc's wording
literally states. The bound below assumes the pessimistic case the module
doc's own words support: every op boundary along the deepest path re-rounds
to fp16.

Deepest-path op count for C-med (n_scales=3, same-res output): stem (1) +
per extra scale (down + down_refine = 2 convs) × (n_scales−1=2) = 4 + per
decode step (resize + up_reduce-conv + concat + up_merge-conv, effectively
2 weighted ops that round their output) × (n_scales−1=2) ≈ 4 + head (1) =
**~10** op boundaries; +2 more (resize + out_refine conv) when output res
is free (**~12**).

Worst-case LINEAR sum (no cancellation — the same conservative framing the
v7 gate's own comment uses): 12 × u16 (4.883e-4) ≈ **5.86e-3**.

`REL_TOL = 1.0e-2` (~1.7× that worst-case bound — headroom for the
UNVERIFIED accumulation-precision assumption, without being so loose a real
wiring bug (wrong layer order, transposed weight layout, wrong stride —
which produces O(1) relative garbage) would slip under it). `ABS_TOL =
5.0e-3` is the floor for near-zero (post-ReLU-dead / bias-only) channels
where a relative measure is meaningless (assert is `abs < ABS_TOL || rel <
REL_TOL`, same OR-shape the house N0 GATE 1 test uses for its own dual
abs/rel check).

## ITEM 3 — FRAME WALL (v7 vs v9), offscreen

### Why `main.rs`/`NetPresent` stays untouched this atom

The REAL IMAGE BAR gate (`verify_stamp`, "NO env override") structurally
refuses to present ANY unstamped weights — v9c included. Wiring
`NetPresent` to accept a U-Net-format checkpoint would add real surface
area to a 5000-line, actively-shared, v7-serving production file for a body
that cannot legally present through it yet; the only way to get a live
`/scry`-driven number through that path would be to manufacture a stamp,
which is exactly what "NO env override" exists to forbid. Scoped instead
as a dedicated offscreen measuring instrument — same "measuring instrument,
not a gate" precedent `examples/onepath_budget.rs`'s own header already
established for a different net class — calling the SAME production types
(`RdirectLive`, `FeatureGatherHistSplit`, `HistoryBuffers`, `UnetLive`)
directly. Full `NetPresent` integration (so a future v9 stamp could
actually ship) is the disclosed remaining gap — UNVERIFIED, not attempted
this atom.

### Method

`examples/rdirect_frame_wall.rs` (new), offscreen, 640×480 (IRON param
default), a slow yaw pan (0.004 rad/frame — same pan step
`real_image_ordeal.rs` uses) so history/reprojection is genuinely exercised
every frame after the first, 8 warmup + 40 timed frames, median/p95.

- **v7**: the EXACT production per-frame GPU sequence
  `main.rs::net_present_frame` runs for `is_v7` weights, GPU-resident start
  to end (no CPU round-trip between trace and net): `Integrator::
  dispatch_split` (evidence, low res) + `dispatch_aov` (gbuffer, native
  res) → `FeatureGatherHistSplit::encode` (GPU-native gather + history
  reprojection, `HistoryBuffers` ping-pong) → `RdirectLive::forward_shared`
  (the real zero-copy pooled MPSGraph forward) [source: packages/scrying-glass/src/main.rs (net_present_frame) + packages/scrying-glass/src/rdirect_live.rs (forward_shared)]. One disclosed simplification:
  the history-swap's source buffer is a dummy same-size buffer instead of a
  real repacked net-output (skips re-importing `EvidenceEngine::encode_pack`
  + the evidence-accumulate/clamp/demod passes, which run AFTER the timed
  region in production and are the same order of cost for both bodies per
  `docs/perf/2026-07-18-neural-live-n0.md`'s own dominant-cost split of
  trace+net) — the swap's own wall cost is a buffer-copy sized by BYTES not
  content, so this doesn't change the measured number, only its realism as
  a rendered image (irrelevant here — this harness never claims a picture).
- **v9**: `UnetLive::forward_gpu_ms`/`forward_cpu_roundtrip` (ITEM 1's
  loader, same trained v9c weights) fed by a CPU-built 41-channel feature
  image (`build_input_img_unet`, ITEM 2's own fn, duplicated a 4th time —
  same house convention). **There is no GPU gather shader for the v9
  channel layout yet** — a real, disclosed asymmetry: v7's gather is
  GPU-native and zero-copy every frame; v9's is CPU-computed (reads back
  the trace buffers via the `trace_headless_*` helpers, builds the 41-ch
  image on the host, uploads it fp16 for the forward) every frame. Both the
  full wall AND `forward_gpu_ms` alone (GPU compute only, no trace/gather/
  readback) are reported, bracketing "what it costs today" against "the
  ceiling once/if a GPU-native v9 gather exists."

### Reading the numbers

v7's full wall (17.43 ms median) sits just over the 16.67 ms budget — one
frame over 60fps by itself, consistent with it being the ALREADY-KNOWN
"live window HUD reads 27.5-34.4ms" class of number this repo's own
`examples/live_loop_audit.rs` documents for the FULL render loop (rays +
skin/tick/splice/upload, not just the net) — this harness's v7 number is
net-path-only (trace-for-the-net + gather + forward), a subset, and still
lands near budget on its own, matching the house understanding that the
net path is a meaningful fraction of frame cost, not the whole story.

v9's full wall (107.96 ms median) is ~6.2x v7's, entirely attributable to
the CPU-side gather (no GPU shader exists for its channel layout) — its
OWN GPU-forward-only number (4.745 ms) is actually **cheaper** than v7's
`forward_shared` call's share of v7's 17.43 ms wall (v7's wall bundles
gather+forward together in this harness, so a direct forward-only
sub-split for v7 isn't isolated here — flagged UNVERIFIED as a precise
delta, but the C-med body's own budget-fit was already established
independently by the STAGE-1 spike doc, reconfirmed above). The dominant
cost is squarely the disclosed gather asymmetry, not the net body itself —
consistent with the STAGE-1 spike doc's own verdict that C-med's GPU-only
forward has 2-2.6x headroom under budget.

## §bridge — ZERO-COPY BRIDGE (V9-WIRE ATOM, BRIDGE FOLLOW-UP, same day)

Scope: kill the two thieves §gather's own decomposition named (7.0ms
readback + 11.9ms fp16-conversion glue, both root-caused to `UnetLive`
opening its OWN `MTLCreateSystemDefaultDevice()` handle instead of sharing
wgpu's Metal device/queue) by building `UnetLive::from_wgpu_queue`,
mirroring `RdirectLive::from_wgpu_queue` exactly at the bridging step (the
v7 house exemplar this atom's own task named). `main.rs`/`NetPresent` stays
untouched (same reasoning as ITEM 3's and §gather's own "why main.rs stays
untouched" sections — no v9 stamp exists yet); no default flipped.

### New code (`packages/scrying-glass/src/rdirect_unet.rs`, `rdirect_gather.rs`, `rdirect_pack16.wgsl`)

- `UnetLive::from_wgpu_queue(wgpu_device, queue, weights)` (new): reaches
  the SAME Metal device/queue wgpu drives via the wgpu-hal Metal backdoor
  (`queue.as_hal::<Metal>()` → `MTLCommandQueue::device()`), byte-identical
  bridging code to `RdirectLive::from_wgpu_queue`. Builds the graph via the
  existing `build_from_weights` (untouched), then wraps the GPU-only
  split's lazily-allocated fp16 INPUT MTLBuffer (`GpuSplit::in_mtl`, already
  existed for `forward_gpu_ms`/`forward_gpu_with_output`) as a wgpu STORAGE
  buffer of `u32` (`feature_buf_u32`, 2 packed fp16 halves per u32) — the
  SAME MTLBuffer bridge pattern `RdirectLive::attach_pool` uses for its own
  pooled feature/output buffers.
- **Synchronization, disclosed and narrower than `RdirectLive`'s own**:
  `RdirectLive`'s S9 pipeline opens SEPARATE net command queues plus an
  `MTLSharedEvent` fence, because it overlaps a net forward with the NEXT
  frame's trace on wgpu's queue (real concurrency, real need for a fence).
  This bridge instead reuses wgpu's OWN queue directly as `UnetLive::queue`
  (the graph forward's own command buffer) — Metal's documented guarantee
  that command buffers committed to ONE `MTLCommandQueue` execute in commit
  order is therefore sufficient alone: the caller's wgpu `queue.submit()` of
  the gather+pack commands (writing `feature_buf_u32`) must happen before
  `forward_gpu_bridged`'s own `commandBuffer()`/`commit()` call, no fence
  needed. Correct for this atom's single-shot measurement use; a future S9-
  shaped double-buffered live-present integration would want the fuller
  `RdirectLive`-style fence, not attempted here (out of scope, see Gaps).
- `rdirect_pack16.wgsl::pack_fp16` (new compute shader) + `rdirect_gather.rs::Fp16Packer`
  (new struct, additive, same house pattern as `FeatureGatherV9`): a
  generic f32→fp16 GPU pack using the `pack2x16float` WGSL builtin (e.x in
  the low 16 bits, e.y in the high 16 — exactly a tightly-packed
  little-endian `[f16,f16]` pair on Apple Silicon, what `MPSGraphTensorData` [source: packages/scrying-glass/src/rdirect_pack16.wgsl + packages/scrying-glass/src/rdirect_gather.rs (Fp16Packer)]
  of `MPSDataType::Float16` expects). Deliberately NOT `enable f16;` native
  WGSL half (that needs the `SHADER_F16` wgpu device FEATURE, requested at
  device-creation time — out of reach for a bridge built from an
  ALREADY-CREATED wgpu device, and this atom's own "no main.rs changes"
  scope keeps device creation untouched). Guarded by `arrayLength` on both
  bindings (no uniform buffer). Dispatch is 2D (`num_workgroups` builtin
  recovers the flat index) because Metal caps a single dispatch dimension
  at 65535 workgroups and the v9 640×480×41 case needs ~98400 — a real bug
  hit and fixed during this atom (first run: `wgpu error: ... dispatch group
  size dimension ([98400, 1, 1]) must be less or equal to 65535`).
- `UnetLive::forward_gpu_bridged` (new): the SAME persistent-compiled-
  executable path `forward_gpu_with_output` uses, MINUS the host
  `f16::from_f32` scalar input-write loop — the caller has already written
  `feature_buf_u32`'s backing MTLBuffer directly via `Fp16Packer`. Both
  methods now share a factored `run_compiled_forward` tail (commit, wait,
  f16→f32 output readout) — `forward_gpu_with_output`'s own behavior/call
  sites are byte-unchanged (refactor only, verified by parity below
  reproducing the SAME numbers pre- and post-refactor).
- `UnetLive::last_encode_commit_ms`/`last_wait_ms`/`last_readout_ms` (new
  probe getters, `Cell<f64>` fields, mirrors `rdirect_live.rs`'s own N0.i
  S13 `last_commit_ms`/`last_wait_ms` house pattern exactly): splits
  `run_compiled_forward`'s CPU wall into its three phases, so the
  forward-wall-vs-GPU-only gap below is a real decomposition, not a lump.
