### 2. Re-derivation from scratch — the two techniques now estimate the same integral
Technique **B** (BSDF sampling), `integrator.wgsl:793-795`, UNTOUCHED:
```wgsl
dir = cosine_hemisphere(n, u1, u2);          // pdf(ω) = cosθ/π
throughput = throughput * tri.albedo.xyz;    // × albedo, nothing else
```
then at the emitter hit `L = L + throughput * tri.emission.xyz * mis_w;` (`:704`).
The per-bounce weight a path tracer applies is `f_r·cosθ/pdf`. Setting
`f_r·cosθ / (cosθ/π) = albedo` gives `f_r·π = albedo` ⇒ **f_r = albedo/π**. The arithmetic
the task asked me to check myself: with f_r = albedo/π, `f_r·cosθ/pdf = (albedo/π)·cosθ·π/cosθ
= albedo` ✔ — the code's plain `× albedo` is exactly right, and it *implies* a normalized
Lambert BRDF. The lobe-selection probability `(1-metallic)` cancels against the branch
probability (the file's own stated convention, `:764-767`), so B's effective BRDF is
`(1-metallic)·albedo/π`.

Corroborating, from a DIFFERENT file this branch does not touch — the CPU reference integrator
states the same convention in its own words:
```
packages/pleroma/src/integrator.rs:9-11
//!   f_r = albedo/π,  pdf = cosθ/π  ⇒  f_r·cosθ/pdf = albedo
//! so each bounce multiplies throughput by exactly the albedo
```
So `albedo/π` is the HOUSE convention, not this reviewer's preference.

Technique **A** (light sampling), post-fix, `:749-750` (identical at `:933-934`):
```wgsl
throughput * (1.0 - metallic) * tri.albedo.xyz * (1.0 / PI)
      * ltri.emission.xyz * ndl2 / pdf_light_sa * mis
```
= `throughput · f_r · L_e · cosθ / p(ω)` with `f_r = (1-metallic)·albedo/π` — **the same f_r as
B**. That is the standard single-sample light-sampling estimator, and it is now the MIS
correctness condition satisfied: both estimators converge to
`E = ∫ (1-metallic)·(albedo/π)·L_e·cosθ dω`. Before the fix, A carried `f_r = (1-metallic)·albedo`,
i.e. π× B's — the defect Finding 4 named.

Both edit sites checked for consistency: `radiance_nee` (`:750`) and `radiance_ed` (`:934`)
are character-identical expressions; `radiance_ed` only differs downstream in bucketing
(`if (diffuse_seen) { d_acc … } else { e_acc … }`). No third NEE site exists —
`grep -n "ltri.emission" ` returns exactly those two lines, both patched.

`pdf_light_sa = (light.pdf/light.area)·dist²/cos_light` is still the correct area→solid-angle
Jacobian with the light-selection pmf folded in; `power_heuristic(pdf_light_sa, pdf_bsdf_sa)`

### 7. The reference-tool ratio claims — algebra says they are plausible, and here is the fine print
The commit message claims, from a 512spp reference render: direct emitter-face ratio pre/post
= 1.000000, NEE-dominated light-pool ratio pre/post = 3.141593 exactly.

**Algebraically supported, with two stated conditions.**
- A pixel whose radiance is entirely the light-sampling term: post = pre × (1/π) exactly, since
  the diff inserts a literal constant factor into a product and touches nothing else in that
  expression (§1). The MIS weight is a function of the two pdfs only, both unchanged, so `mis`
  is bit-identical for the same sample — and the RNG stream is bit-identical too (§1), so the
  comparison is same-sample-path, not two noisy renders. Ratio π to the last printed digit is
  therefore *expected*, not lucky. **Plausible.**
- Direct emitter faces: the primary-hit emission at `:704` uses `mis_w = 1` (the MIS branch
  requires `bounce > 0`), so the dominant term is untouched → 1.000000. **Plausible.**
- CONDITION A: `1.000000` is exact only if the pixel's *secondary-bounce* NEE contribution is
  zero. It generally is not — it is merely negligible against a bright emitter's own radiance.
  So `min=max=mean=1.0` over 2024 px is a statement about print precision, not an algebraic
  identity. Correct as reported; would be wrong if read as "provably exactly 1".
- CONDITION B: `exactly π` requires `GAIA_NEE_CLAMP = 0`. The `(1.0/PI)` is applied INSIDE
  `clamp_nee_radiance(...)`'s argument (`:749-750`), and that clamp is non-linear
  (`c * (clamp_v/m)` above threshold). With a clamp armed, a π-smaller value clamps differently
  and the ratio would land in `[1, π]`, not on π. Default is 0.0 (`integrator.rs:412`,
  `env_f32("GAIA_NEE_CLAMP", 0.0)`; shader `:207` `if (clamp_v <= 0.0) { return c; }`), and the
  quoted verify run does not mention setting it — so the claim stands, but it is
  clamp-off-conditional and the commit message does not say so. **NIT, not a defect.**
